# Leonida Log design

**Visual source of truth:** the [design reference](https://claude.ai/artifact/FL8isDnFAyobGqPrkFeb9W). It has the chosen screens in light and dark, every component, the logo, palette and type. Component names below match it.

Built from the [idea page](https://github.com/dividedby/ideas/tree/main/projects/leonida-log) Decisions and Research. Visual rules are in [branding.md](branding.md). Decisions are recorded in [docs/adr/](adr/). The [design review](https://claude.ai/artifact/UeXqmdUW34qdRoMSfq4kg8) is decision history only: A Postcard in all sections.

## Goals

- Know what to do **before each point of no return**, and go into the next chapter as strong as possible.
- Track progress (checklist items, stats) from my phone while I play.
- Never spoil anything past the mission I'm on.

## v1 scope

- **Story position:** set the current mission. It drives every spoiler gate.
- **Before-you-move-on checklists:** one for each point of no return, starting with Tourist Trap in Chapter 1, grouped by category.
- **Stats:** Strength, Cardio and Focus (levels 0-4) for Jason and Lucia, set by hand. No workout log (ADR 0009).
- **Romance / relationships** and **criminal profile** sections. Both are research-first, so they start thin and fill in as data is curated.
- **Data pipeline:** curated data in the repo, scrapers enriching a server database.
- **Out of v1:** the map (v2) and push notifications for stat decay.

## v2 scope

- **Map:** the checklist's rows placed by area on an original schematic of Leonida, with an area sheet per reached area and an "Anywhere" list (ADR 0010, plan in [plans/v2.md](plans/v2.md)). Regions in v2.0, districts later.
- **Out of v2:** collectibles, points of interest (gyms, stores), exact pin positions, pan and zoom, offline mode.

## Components

In `components/<Name>/` (a component plus its CSS module). All are server components except ChecklistRow. MarkDone isn't in the design reference: it's a form (or link) styled as PrimaryButton. `/components` shows each one in both themes at 375px; it is `noindex`. Tokens and contrast: [branding.md](branding.md).

- **PostcardHeader** `{ eyebrow?, title, subtitle?, badge?, level? }`: `level` 1 (default, `h1`) or 2. Sun and sea are decorative.
- **ExitSign** `{ exit, gateTitle, done, total, href? }`: no description prop, so it can't carry text about the gate (ADR 0002).
- **StatRing** `{ level, label, size? }`: `md` (number and label) or `sm` (ring only). `level` is clamped to 0-4 (`lib/stat-level.ts`, client-safe). The ring is `role="img"`.
- **StatStrip** `{ rows, href? }`: one row per character, mini rings plus level.
- **CategoryHeader** `{ title, done, total }`, **ProgressBar** `{ done, total, label? }` (`role="progressbar"`, 0-100), **PrimaryButton** `{ children, type?, onClick?, formAction?, disabled? }` (44px minimum).
- **Chip** `{ variant, children }`: `soon-lost`, `tip` or `countdown`. The countdown text comes from `countdownLabel`. The reference's "Research" chip is dropped: nothing in the app is labelled by confidence (ADR 0008).
- **LockedRow** `{ count, unlockMission }`: "4 more unlock after Day Release"; shows no item text.
- **TabBar** `{ active }`: `nav` "Main" with Story, Checklist, Stats and More. v2 makes it five: Story, Checklist, Map, Stats, More (ADR 0010).
- **ChecklistRow** (client) `{ id, label, checked, action?, onToggle?, chips?, disabled?, href? }`: a real checkbox in a 44px label. Toggling submits a form whose FormData holds `id` and `checked` (`"true"` or `"false"`, the new state); `action` is a server action taking that FormData, so screens bind it without changing the component. The box flips at once (`useOptimistic`) and settles on the `checked` prop when the action finishes. `href` adds a details chevron (44px, `aria-label` "Details: {label}") beside the label, outside it, since a link inside the label would toggle the box. `disabled` greys the box and label.
- **MarkDone** `{ control, returnTo, action }`: "Mark mission done" for Home and the checklist. `control` is `doneControl`'s result: `advance` renders a one-tap form (FormData `from` = the current mission's global order, `return`), `confirm` renders a link to `/done`, null (last mission) renders nothing. The label names no mission.

## Screens

Components: PostcardHeader, ExitSign, StatStrip, StatRing, CategoryHeader, ChecklistRow, Chip, LockedRow, ProgressBar, PrimaryButton, MarkDone.

### Home

This is round 2, option A.

- **PostcardHeader:** "Chapter N · Name" (the current mission's chapter is reached, so its name shows), the current mission, and "Mission N of M". N is the mission's number inside its chapter and M the chapter's mission count (`Chapter.missionCount`), so "Mission 9 of 22" in Chapter 1.
- **ExitSign** for the next point of no return: "EXIT 20 · Tourist Trap · 3 of 6 done". The exit number is the gate mission's number inside its chapter. Done and total count the gate's checklist rows (visible items plus opened optionals) at the current mission. The gate's mission is named before it is reached; what happens in it is not (ADR 0002). It links to `/checklist`.
- **StatStrip:** a compact strip with one slim row per character and three mini rings, tapping through to Stats. It's smaller than the round 2 mockup, per the feedback that the 3-stat card takes up too much space. Missing stat levels show as 0.
- **Up next:** up to 3 unchecked ChecklistRows from the gate's list, leaving out rows whose cutoff has passed (they can't be done; they stay in the checklist and in done/total). Rows with an open cutoff come first, fewest missions left first; the rest follow in list order. Every row with an open cutoff shows its countdown chip; "Soon lost" shows too when the cutoff is 3 or fewer main missions away (`SOON_LOST_WITHIN` in `lib/home.ts`; 4 or more shows only the countdown). Ticking submits `setItemChecked` (`app/actions.ts`), which only accepts rows `isTickable` allows at the current mission. Empty: "All done for Exit N." when every row is ticked, otherwise "Nothing left you can still do for Exit N." (the rest are past their cutoff).
- **After the last gate:** no ExitSign; Up next lists the opened safe-to-leave optional missions not yet ticked, and when none remain, "No more points of no return."
- **See all** next to the Up next heading links to `/checklist`, where ticked rows stay listed and can be unticked.
- **Mark mission done** (Flow 3) below the list: one tap for an ordinary mission, a link to `/done` when the current mission is a point of no return, nothing on the last mission.
- **Change story position** link to `/onboarding`.
- **Tab bar:** Story, Checklist, Stats, More. v2 adds Map between Checklist and Stats.
- **Error:** `app/error.tsx` shows a fixed message and a retry button, never the error text.

### Before you move on (checklist)

This is round 2, option A.

Built in `app/checklist/page.tsx` from `checklistView` (`lib/checklist.ts`); the page only renders it.

- **PostcardHeader:** "Before you move on" as the eyebrow, the next gate's name and "N of M done". N and M count every row for the gate (visible items plus opened optionals), closed rows included, so the figure matches Home's ExitSign. After the last gate: the title "Before you move on" and "No more points of no return.", no count.
- **CategoryHeader** for each category in the curated order (`CATEGORIES`), empty ones skipped, with done/total, and ChecklistRows under each. Order inside a category is file order. "Optional missions" follows (most urgent first), then "Safe to leave" (opened optionals that never close; it shows whenever any are open, also before the last gate), then "No longer available". Safe to leave isn't part of the gate's N of M.
- **Ticked rows stay listed**, checked and without chips, so a row ticked on Home (where it leaves Up next) can be unticked here.
- **Closed rows:** an unticked row past its cutoff goes to "No longer available" at the bottom: disabled, no chip, counted in the header's M but not in any category count. A ticked closed row stays in its category, enabled, so it can be unticked.
- **Chips:** "Soon lost" for rows whose cutoff is 3 or fewer main missions away, no confidence chip: every entry shows its best-evidence value unlabelled (ADR 0008). Cutoffs show as a countdown from `closesIn` and `countdownLabel` ("Closes in N missions", "Do this before your next story mission" at 1), never by naming the closing mission.
- **LockedRow:** "4 more unlock after Day Release", naming the mission that unlocks the earliest locked item for the gate. The count includes optional missions that haven't opened yet, and the mission named is always a main mission (an optional's anchor). The count and that mission title show; the content doesn't (ADR 0002). Absent when nothing is locked.
- **Derived rows:** each opened optional mission bound to the gate shows as a checklist row with its countdown, most urgent first, and can be ticked.
- **Lost list:** a card under the rows with the gate's `lost` entries and a countdown line from `closesIn(data, current, gate.mission)`, for the next gate only (ExitSign's gate), hidden once the gate is the current mission. `/done` shows the list again (see Flow 3).
- **Mark mission done** at the bottom (MarkDone, as on Home).
- **Details:** each row's chevron opens `/checklist/item/[id]` (server-rendered, no client JS): the title, a "Back to checklist" link, the countdown chip or "No longer available", how-to and location (items) or the character and note (optional missions), and source links (`target="_blank"`, `rel="noopener noreferrer"`). Only visible items and opened optional missions have one (`isTickable`); anything hidden or unknown is the same 404, and the tab title stays "Leonida Log". Curated fields only: never `verified`, `evidence` or scraped data. A source whose title or link names a main mission after the current one is withheld (the entry's own gate may be named, as in its text): source titles and URLs are curated from outside and name missions the item text may not.
- **Logic** lives in `lib/checklist.ts` (`checklistView`, `itemDetail`) and `lib/done.ts`, tested against the fixture and, for leaks, every mission as the current one on the real data.

### Stats

This is round 1, option A, without the workout button and "Last workout" line (ADR 0009).

- PostcardHeader "Stats" with "Max level is 4". One card per character (Jason, then Lucia) with three StatRings: Strength, Cardio, Focus. Then the Tip chip: "Strength and Cardio can slip. Focus levels stay." There are no how-to links: no curated source backs one.
- **Tap a ring to set its level.** Each ring is the `<summary>` of a native `<details>` (no client JS). It opens a 0 to 4 picker of five 44px buttons under the ring, the current level marked with `aria-pressed`. One tap submits `setStatLevel` (`app/stats/actions.ts`) with the character, the stat and the target level, never a delta, so a double tap can't drift. A level change re-keys the `<details>`, which closes it. The summary's label ("Strength for Jason, level 3 of 4. Change") names the ring, so the ring itself is hidden from assistive tech; the buttons read "Set Strength for Jason to 2".
- `parseStatLevelInput` accepts only exact `0` to `4` for a known character and stat; anything else is rejected before any write. `statsView` (`lib/stats.ts`) builds the cards; Home's `statRows` derives from it. A stat with no row is level 0.
- Stats are not spoiler-gated: they hold the user's own levels and no curated content.

### Map (v2)

Decided in ADR 0010; plan in [plans/v2.md](plans/v2.md). The design reference's Map (v2) section has the chosen Map screen, area sheet, Home with area tags and the five-tab TabBar in light and dark (picked 2026-11-27: the coastline schematic and the inline tag).

- **PostcardHeader:** "Map" with the next gate as the eyebrow ("Before Tourist Trap"), as the checklist names it.
- **Schematic:** one static SVG coastline of Leonida with its regions as shapes, drawn by hand, not to scale and not traced from any map, the Leonida Keys as one tappable island chain, fit to the phone width, no client JS, no pan or zoom. A reached region is a link (44px minimum hit area) with its name and a badge counting the unticked rows its area sheet shows (districts roll up). An unreached region is an unnamed shape in the rule colour: no name, no badge, not a link, `aria-hidden`. Sea and coast are decorative.
- **No locked counts** anywhere on the map: a per-area count would say where hidden content is. The checklist's LockedRow is the only place locked counts show.
- **Anywhere:** below the schematic, a CategoryHeader "Anywhere" with the map's rows (the next gate's visible items and opened optionals plus safe-to-leave optionals, closed rows left out) that have no area, as ChecklistRows.
- **Area sheet** (`/map/[area]`): server-rendered. PostcardHeader with the area name, a "Back to map" link and the area's rows as ChecklistRows: the next gate's visible items and opened optionals plus safe-to-leave optionals, filtered to the area (a region includes its districts), with countdown and "Soon lost" chips and the detail chevron. Closed rows are left out. A hidden area, an unknown slug and a district before its region give the same 404, and the tab title stays "Leonida Log".
- **Row area tag:** a ChecklistRow whose entry has an area shows the area name in muted text after the label on the same line, after a dot ("· Leonida Keys"), on `/checklist`, Home's Up next and area sheets (left out on an area sheet when it would repeat the sheet's own area). No colour, so it doesn't read as a chip.
- **Detail pages:** "Area: {name}" under the title, linking to `/map/[area]`.
- **Logic** lives in `lib/map.ts` (`mapView`, `areaSheet`) on top of the rows of `checklistView`'s sections, tested on the fixture and, for leaks, every mission as the current one on the real data.

### More

- **Story position:** the current chapter, mission and "Mission N of M" (chapter-relative, as on Home), with "Change story position" linking to `/onboarding`. Nothing past the current mission is named (`lib/more.ts` leak tests run every mission as the current one).
- **Romance** and **Criminal profile:** non-link rows reading "Research in progress". `data/curated` has nothing for either, and the relationship facts under Open questions are later-story spoilers, so none is rendered. Research-first plan: a later `data/curated/*.yaml` must carry `visible_after_mission` on every entry, with zod validation and leak tests, before a screen shows any of it.
- **Settings:** the theme as three buttons (System, Light, Dark) with `aria-pressed`, posting `setTheme` (`app/more/actions.ts`). The root layout reads the saved theme per request and sets `data-theme` on `<html>` (absent for System, so the OS preference applies), so a change shows on the next render with no flash. The viewport `themeColor` stays media-based, so the browser chrome follows the OS, not the setting. A read-only line says "Spoilers: safe. Opening later content isn't available in v1."; the spoiler-mode control is deferred (ADR 0002), and `setSpoilerMode` and the column go unused.
- With no saved mission, `/more` redirects to `/onboarding`, as Home does.

### Flows

1. **First run:** pick the current mission and land on Home. Chapters show as "Chapter N" until reached. Within the chosen chapter, missions are listed by number, and a title shows only for the one you select. `/onboarding` is a server-rendered GET flow: `?chapter=<n>` then `?chapter=<n>&mission=<global order>`, numbers only (slugs spell titles, so no slug reaches the client, a URL or a form). The selected row's form posts the global order to `saveStoryPosition`, which maps it to a slug (`lib/picker.ts`) and redirects Home. The same route is the story position picker once a mission is saved, with a Cancel link. A hand-edited `?mission=` shows that mission's title; accepted for a single user behind Access.
2. **Play session:** open Home, tick items, and set a stat level when it changes.
3. **Mark mission done** (Home and the bottom of `/checklist`): an ordinary mission moves on with one tap and no confirmation. At a point of no return the control links to `/done`, which names only the current mission, lists what the gate loses (even though the checklist hides that once the gate is current: the last chance to see it), counts the gate's unticked rows that can still be done and offers "Mark done and move on" (posting `confirmed=true`) or Cancel. The server action (`markMissionDone`) takes the current mission's global order as `from`: a stale or repeated form changes nothing and goes Home, crossing a gate without `confirmed` is rejected, and the move is one mission (`advanceTarget`). After a gate it lands on `/checklist`, which now shows the next gate; otherwise it returns to the page the form came from (`return`, limited to `/` and `/checklist`). On the last mission there is no control and no "completed" state. The story position picker reverses a mis-tap.

## Data model (sketch)

- `chapters` (5) and `missions` live together in `missions.yaml`. The 92 main missions are KeenGamer's 91 plus Pool Day (the count is disputed, see Open questions, and gtabase counts 109 entries, see the header of `missions.yaml`). Among the mains, list position is the canonical order; order is derived on load and never stored, so it can't disagree with the list. Order is the spoiler gate.
- Mission kinds: `main` (default), `optional`, `strangers-and-freaks`, `hourglass`, `side-job`. Every non-main mission also carries `character` (`jason`, `lucia` or `both`), `opens_after` (a main or optional mission slug), `closes_at` (a main mission slug or `never`), `sources[]` and an optional `note`; a main mission sets none of them. Any mission may carry an optional `evidence` (as on items: background only, never rendered, ADR 0008). The 78 optional missions entered so far sit after the mains in `missions.yaml`; they have no order of their own, so chapter counts (22/11/26/26/7) and gate orders (20/33/59/84) come from the mains only and never move. `never` is a reserved slug.
- `lib/curated.ts` derives `data.missions` (mains only; the current mission, the picker and `setCurrentMission` read it) and `data.optionalMissions` (`opensAnchor`, the main mission at the end of the `opens_after` chain; `opensOrder`, its order; `closesAt`; `closesOrder`, null for `never`), sorted by `opensOrder`. An optional opens when the player reaches its anchor and closes when they reach `closes_at`. Its gate is the first gate at or after `closes_at`; `never` has none.
- `gates.yaml`: missions that are points of no return, keyed by mission slug, with what you lose (e.g. Tourist Trap → Ultimate Edition vehicles, free roam as Jason). Tourist Trap, Checking Out, The Cartel Heist (the Bayside Safehouse, per Beebom and gta.wiki) and Sunset (free roam, the BuckMe balance, weapons/equipment/outfits and the Y Hotel suite, all temporary) are listed.
- `items/<gate-slug>.yaml`, one file per gate: id, title, category, `before_gate` (the gate's mission slug), `visible_after_mission` (the single visibility field), optional `lost_at_mission`, `verified`, optional `evidence` (`basis`, optional `note`; background only, never rendered, ADR 0008), `how_to`, optional `location`, `sources[]` (url, title, accessed date). Items exist for the four gates (Tourist Trap, Checking Out, The Cartel Heist and Sunset); Unfinished Business has no gate or items, by decision (see Open questions).
- Item text (title, how_to, location) names no mission after its `visible_after_mission`, except its own gate's title; earlier cutoffs live only in `lost_at_mission` (ADR 0002, amended 2026-11-26). The app shows "Closes in N missions" / "Do this before your next story mission" from it and from `closes_at` (ADR 0002, second amendment, 2026-11-26); UI not built yet. Optional-mission titles and notes follow the same rule from their `opens_after` anchor, and no gate `lost` entry names a mission. A mission slug and an item id may not collide (`item_checks` stores both under one key); the repository lets an optional mission's slug be ticked like an item.
- `areas.yaml` (v2, ADR 0010): areas with `slug`, `name`, `visible_after_mission` and optional `parent` (a region slug; districts only, later than v2.0). Items and optional missions gain an optional `area` slug. Rules: a known area; an item's area visible no later than its `visible_after_mission`, an optional's no later than its opens-after anchor; a district visible no earlier than its region; no item or optional text names an area before the area is visible.
- `lib/curated.ts` validates all files and the rules across them (known refs, `visible_after` and `lost_at` no later than the gate, `lost_at` not before `visible_after`; for optional missions, a resolvable `opens_after` chain with no cycle, `closes_at` a main mission or `never`, `opens_after` no later than `closes_at`, `closes_at` no later than the last gate) and fails on any issue. `lib/curated-load.ts` reads the files, server only.
- `lib/gates.ts`: `isVisible`, `nextGate` (a gate you're on isn't passed yet), `lockedSummary` (count plus unlock mission, optionals included), `closesIn` (a countdown: `open` N missions, `closed`, or `never`; standing on the closing mission counts as closed), `countdownLabel` (the UI text, null when closed or never), `gateOptionals` (opened, unclosed optionals for a gate, most urgent first), `safeToLeave` (opened optionals that never close), `isTickable` (a visible item or an opened optional; the write-side guard), `missionsInChapter` (ids and numbers), `missionTitle`, `pickerChapters`. It never returns titles, except through `missionTitle`. The current mission is always a main mission; an optional slug throws.
- `lib/picker.ts` (`pickerView`, `missionFromOrder`) and `lib/home.ts` (`gateChecklist`, `gateProgress`, `upNext`, `chipsFor`, `statRows`, `storyPosition`, `homeView`), `lib/stats.ts` (`statsView`, `parseStatLevelInput`), `lib/settings.ts` (`parseTheme`, `themeAttribute`, `settingsView`) and `lib/more.ts` (`moreView`) are the pure view models and form parsers the screens render; pages hold no logic. `lib/server/data.ts` (server only) memoises `getCurated()` and `getRepository()` per process, so a curated YAML change needs a restart. Pages that read the database are `force-dynamic` (the build has no `DATABASE_PATH`); so is the root layout, which reads the theme from `progress` (every route except the manifest and icon is dynamic).
- SQLite via Drizzle (`lib/db/schema.ts`, SQL in `drizzle/`, applied by `pnpm db:migrate`; see ADR 0004). Timestamps are ms-epoch integers. Curated ids (mission and item slugs) are plain text with no foreign key; `lib/db/repository.ts` validates them against curated data before writing.
- `progress`: single row (id = 1), created on the first write. `current_mission` is null until onboarding; `spoiler_mode` is `safe` or `open` (default `safe`); `theme` is `system`, `light` or `dark` (default `system`).
- `item_checks`: checked item ids with `checked_at`.
- `stat_levels`: level 0-4 per character × stat (Strength, Cardio, Focus).
- No workouts table: ADR 0009 dropped the workout log, and migration `0002_drop_workouts` removed the table.
- `sources` (scraper module id, url, title, host, HTTP validators, remote and content hashes, check and change times, the latest normalized `extract`) and `candidates` (source, gate, category and mission hints, `change_kind` `new`/`modified`, `diff_summary`, `raw_extract`, status `new`/`promoted`/`rejected`): scraper-owned, server only, `extract` and `raw_extract` are never rendered. The repository doesn't expose them yet. How the scrapers fill them: [scrapers/README.md](../scrapers/README.md).
- Romance and criminal profile get their own tables once research shows what's trackable.

## Data sources and refresh

- **Curated (in repo):** `data/curated/*.yaml` covers missions, gates and items at their current best-evidence value (ADR 0008). It's the source of truth and is reviewed by hand.
- **Scraped (server only):** scrapers fetch guide pages and store raw extracts with URL and fetch time in the server database. Nothing scraped is committed.
- **Merge:** scraped facts become _candidates_, and are promoted to curated after review. The app shows only curated items, never a candidate or a confidence label (ADR 0008).
- **Refresh:** manual runs, plus a light weekly systemd timer with Discord alerts while launch-period guides are still changing.
- **Spoiler safety:** every item needs a `visible_after_mission`. Scraped text is never shown raw, because guide pages mix later spoilers in.

## Architecture

- **App:** Next.js (App Router) + TypeScript, server components, with server actions for writes. Installable PWA, phone-first.
- **Database:** on the server (SQLite with Drizzle, one file on a volume, since it's a single user on a small box; see ADR 0004).
- **Hosting:** docker compose on the Hetzner VPS behind a Cloudflare Tunnel with Cloudflare Access (Google SSO) at gta.dvdby.cc. CD runs from GitHub Actions.
- **Scrapers:** a separate small Node CLI in the same repo, run by a timer, with polite rate limits and robots.txt respected (ADR 0007); terms of use don't restrict which sources are fetched (see Scraping terms of sources).

## Risks

- **Scraping terms:** some guide sites forbid it (IGN, KeenGamer, Polygon, GameSpot). Keep the data private, attribute sources, and drop a source module if its site objects. [docs/sources.md](sources.md) ranks the sources, records each site's robots.txt and fetch method, and says which ones get a scraper.
- **Launch-week accuracy:** guides disagree and update daily. Hence best evidence with a tie-break toward the safe value, weekly re-research, and source links (ADR 0008).
- **Spoiler leaks** through scraped text or item titles. Mitigated by gating every item and never rendering raw scrapes.
- **Rockstar IP:** don't use official art or logos. Any public launch would need another look at names and assets.
- **Small VPS:** scrapers must stay light, with no headless-browser farms on the box.
- **Stat decay tracking:** the exact rules are unknown, so v1 has levels set by hand, no workout log and no notifications (ADR 0009).

## Settled at build start (2026-11-25)

- Checklist keeps A's done/total count per CategoryHeader; no per-category progress bar.
- Stat decay: no workout log (ADR 0006 planned one; the owner dropped it, ADR 0009), no reminders.

## Open questions
